## 上下文

`add-changelog-page` 变更此前明确决定"不引入全局 i18n 框架"，因为当时需求仅限单页面双语。本次需求扩大到全部 Admin 页面，该决策不再成立，需要重新做架构选型。

## 目标 / 非目标

**目标：**
- 引入可长期维护、可扩展的 i18n 方案，覆盖全部 Admin 页面
- 语言偏好持久化，跨刷新/跨登录会话保持
- 设置页面视觉重构为 iOS Tableview 风格

**非目标：**
- 不追求专业级翻译质量
- 不为未来可能的第三种语言做特别设计
- 不引入浏览器语言自动检测

## 决策

1. **i18n 库选型：`react-i18next`，而非自建 Context+字典**
   - 对比：自建 `LanguageContext` + 手写字典 vs `react-i18next`
   - 选择 `react-i18next`，因为：覆盖范围已扩大到全部页面（约 20 个组件），社区成熟方案在插值、命名空间、按需扩展语言上更省心；自建方案在这个规模下需要重新发明 `react-i18next` 已解决的问题（更新触发、SSR 兼容性等），不划算

2. **语言持久化：手动 `localStorage` 读写，不引入 `i18next-browser-languagedetector`**
   - 对比：`i18next-browser-languagedetector` 自动检测 + 持久化插件 vs 手动读写
   - 选择手动读写，因为：本次明确不做浏览器语言自动检测，只有中/英两种固定选项，用一行 `localStorage.getItem`/`setItem` 即可满足，引入检测插件是过度设计

3. **更新日志内容的双语来源：保留后端 `{ zh, en }` 字段，不迁入 i18n 资源文件**
   - 对比：把每条 changelog 文案也做成 i18n key vs 保留现状的后端双语字段
   - 选择保留现状，因为：changelog 内容是随版本发布变化的业务数据（每次发版都要新增一条），本质上不是界面词条；强行塞进 i18n 资源文件会让每次发版都要同时改前端资源文件，反而增加维护成本。前端只需把"选哪个字段渲染"的判断依据从页面本地 state 改为 `i18n.language`

4. **设置页面视觉：内联实现 Tableview 布局，不新增通用 UI 组件**
   - 对比：抽象出 `ui/list.tsx`/`ui/list-row.tsx` 通用组件 vs 直接在 `settings-panel.tsx` 内实现
   - 选择内联实现，因为：目前只有设置页面这一处需要该样式，抽象成通用组件属于为未来假设的需求做投机设计；沿用现有 `Card` 作为分组容器 + Tailwind `divide-y` 即可满足视觉要求

5. **翻译 key 命名：按页面命名空间分组，`common.*` 存放跨页面复用词**
   - 对比：单一扁平 key 空间 vs 命名空间分组
   - 选择命名空间分组，因为：约 20 个组件、数百个词条，扁平命名极易冲突且难以定位来源；命名空间与组件文件一一对应，便于阶段 3 按文件拆分任务

## 风险 / 权衡

- **权衡**：引入新依赖 `react-i18next`/`i18next` 换取长期可维护性，评估为合理（覆盖范围已是全局级别，自建方案的长期维护成本更高）
- **风险**：约 20 个文件的文案迁移工作量大，遗漏风险通过阶段 3 末尾逐页核对任务缓解，不做自动化扫描工具（本次不引入静态扫描"是否还有硬编码中文"的脚本，属于超出本次范围的额外工具建设）
