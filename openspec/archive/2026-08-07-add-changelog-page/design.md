## 上下文

Admin 控制台已有 `build_model_list()`（`src/anthropic/handlers.rs`）这一"编译期静态数据 + Admin API 暴露"的成熟模式（支持模型列表）。本次新增更新日志功能面临三个需要显式决策的技术选型：数据存储位置、是否引入 i18n 框架、页面接入方式。

## 目标 / 非目标

**目标：**
- 复用项目已验证的静态数据模式，最小化新增复杂度
- 支持中英双语内容展示，但不扩大到全局 i18n 改造

**非目标：**
- 不做运行时可编辑的 changelog 配置（不面向"由 Admin 在界面上编辑更新日志"的场景）
- 不做自动化生成流水线（不追求 changelog 与 commit 历史强绑定/自动同步）
- 不引入前端路由库（`react-router` 等），沿用项目现有 `activeTab` 状态机模式

## 决策

1. **数据存储：后端 Rust 静态数据，而非配置文件**
   - 对比：`app/config/*.json` 类运行时配置文件 vs 编译期硬编码
   - 选择编译期硬编码（`src/admin/changelog_data.rs`），因为：changelog 内容与代码版本强绑定，理应随代码提交一起进入版本控制历史；避免引入文件读取失败、格式校验、模块热加载等运行时复杂度；与现有 `build_model_list()` 模式保持架构一致性

2. **双语实现：页面级 `useState`，而非全局 i18n 库**
   - 对比：`react-i18next`/`next-intl` 等通用国际化框架 vs 页面内简单状态 + 数据结构自带双语字段
   - 选择后者，因为：项目当前 0 处 i18n 基础设施，引入通用框架收益（可扩展到其他页面）与本次需求（仅一个页面双语）不成比例；数据结构 `{ zh: String, en: String }` 已经能满足当前场景，且未来若要扩展到全局 i18n，该数据结构可以平滑迁移

3. **页面接入方式：沿用 `activeTab` 状态机**
   - 对比：引入 `react-router` 做真正的 URL 路由 vs 沿用现有 `dashboard.tsx` 状态机模式
   - 选择沿用现状，因为：全项目其他页面均无 URL 路由，单独为这一个页面引入路由库会造成架构不一致，且超出本次提案范围（不做通用改造）

4. **API 端点组织：新增独立 handler 文件**
   - 新增 `src/admin/changelog.rs`（不复用 `api_keys.rs`），路由统一注册在 `src/admin/router.rs`，复用现有 Admin 鉴权中间件，不新增权限判断分支。选择独立文件而非并入 `api_keys.rs`，因为二者职责不同（API Key 管理 vs 只读展示数据），与项目现有按领域拆分 handler 文件的习惯一致

## 风险 / 权衡

- **权衡**：静态硬编码意味着每次发版需要开发者手动同步内容，牺牲自动化换取实现简单性与架构一致性，评估为合理取舍（changelog 更新频率远低于代码提交频率，人工维护成本可控）
- **风险**：双语内容依赖人工翻译质量，初期数据量小（6 个版本），可接受
